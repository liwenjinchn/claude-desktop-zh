# 实施过程、本机环境与测试总结

记录日期：2026-10-16，时区 Asia/Taipei。本文记录已发生的检查和实验，未来支持计划不作为测试结果。

## 最初的问题

同一台电脑的 Claude Desktop 在普通模式可选择简繁中文，切到 magpie 等工具配置的 3p Gateway 后，主界面只提供其他语言。最初读到普通模式 `config.json` 的 `locale: zh-Hans`，但运行中的 3p 仍显示英文。

后来通过真实进程参数确认，普通模式和 3p 使用不同数据目录。不能仅凭 `%APPDATA%` 下某个配置判断当前进程的界面语言，也不能仅凭使用了非官方模型断言某个进程处于 3p。

本机确认过两种界面来源：普通模式为 `https://claude.ai/...`；3p 为 `app://localhost/...`。程序源码也分别返回在线站点和本地协议地址。

## 查明的语言机制

程序有不同层的翻译资源：

- 桌面外壳的 `resources/zh-Hans.json` 与 `zh-Hant.json`，旧版各 619 条，主要是原生菜单和桌面功能。
- 3p 主界面的 `resources/ion-dist/i18n`，旧版英文 34,954 条，新版英文 35,441 条，但检查时都没有简繁中文文件。
- 正常模式从在线站点取得的主语言包、动态文案和 frame-shell 翻译。中文并非全都随安装包交付。

因此不能把 619 条外壳翻译复制到主界面，就期望补齐数万条消息。先前关于“只有这么点中文”的描述应限定为安装包中这套外壳资源，而非整个产品的翻译能力。

前端还会调用 `window.electronIntl.requestLocaleChange(locale)`，把主界面语言同步给外壳；桌面进程再写入语言配置。在前端回退英文时，外壳的中文设置也可能被覆盖。

检查 magpie 当时源码，未发现其 Claude 接入逻辑写入 `config.json` 的语言字段。该证据支持 Claude 自身同步造成覆盖，但没有抓取进程级文件写入追踪，因此没有声称独立确认每一次写入者。

## 实验经过

### 配置与开发者工具

1. 备份 3p 配置，仅把 `locale` 从 `en-US` 改为 `zh-Hans`，正常重启后又变回英文。
2. 检查安装包函数，在隔离环境验证前端同步请求可以覆盖外壳语言。
3. 临时启用官方 Developer Mode，打开开发者工具。控制台的粘贴保护由用户本人确认，代理未代替绕过。
4. `electronIntl` 及其 `requestLocaleChange` 属性均为不可写、不可重新定义，普通控制台替换函数失败。
5. 通过原有接口请求 `zh-Hans` 和 `zh-Hant`，真实菜单立即分别显示简体和繁体。主界面仍为英文。这证明外壳能加载中文，但未解决主界面翻译，也未阻止后续同步。
6. 测试后恢复临时开发设置。曾按用户要求留下简体外壳供查看；后续完整方案不依赖控制台。

### 独立程序副本

`WindowsApps` 拒绝写入。没有修改所有权、ACL、EXE fuse、ASAR 或完整性校验。

复制程序后确认能脱离商店包启动，但首次只设置 `CLAUDE_USER_DATA_DIR` 时，该变量被程序忽略，副本用了默认目录。随后用 `--user-data-dir` 隔离 Chromium 数据，并通过子进程的 `LOCALAPPDATA` 把 3p 部署配置和数据也指向测试根目录，才确认隔离成立。

这解释了为何必须通过本项目 `launch` 启动，直接运行副本 exe 不保证使用测试数据。早期新产生的普通配置被保存在工作区，不作为用户现有资料删除。

### 提取官方语言

在正常中文模式的 HTTP 缓存中找到官方 URL：

```text
https://claude.ai/i18n/zh-Hans.json
https://claude.ai/i18n/dynamic/zh-Hans.json
https://claude.ai/i18n/frame-shell/zh-Hans.json
```

实际请求还带版本查询参数。直接 HTTP 下载在本机遇到 403，所以采用只读缓存导入，解码 Brotli 响应。随后临时选择官方繁体，取得对应 `zh-Hant` 基础和动态资源，并将正常模式恢复简体。

资源的响应哈希、规范化 JSON 哈希、来源 URL 和导入时间保存在本地 `.catalogs`。不保存完整 HTTP 缓存、不导出账号令牌。候选基础包按本地英文键集匹配率选择，不盲目采用时间较新的文件。

## 本机环境

本次只在 Windows 实机执行，未在 Mac 或 Linux 桌面运行 Claude。没有采集 Windows 具体版本号或处理器型号，不补写未经确认的信息。

- 初期 Claude：商店包 `Claude_2.37337.1.0_x64__pzs8sxrjxfjjc`。
- 完整汉化验证：商店包 `Claude_2.42304.0.0_x64__pzs8sxrjxfjjc`。
- 安装形态：WindowsApps 下的 MSIX，外置 `resources/ion-dist`。
- Node：项目运行和测试时观察到 `v24.14.0`，项目最低声明为 Node 22。
- magpie：本次补充查询可执行文件报告 `0.1.1234`，Windows amd64，网关监听 `127.0.0.1:3425`。未用二进制版本号推断其对应远端源码版本。
- 网关模型：界面实际显示 Kimi Code 模型目录。仅验证目录和界面，没有发送模型请求或启动代码任务。
- 工作区：项目源码位于 `outputs/claude-desktop-3p-zh`，应用副本和原始实验位于同级工作区 `work/`，二者分开。

常见本机路径使用变量表达，避免把用户名和密钥写进开源文档：

```text
普通模式实际存储：
%LOCALAPPDATA%/Packages/Claude_pzs8sxrjxfjjc/LocalCache/Roaming/Claude

早期 3p 实际存储：
%LOCALAPPDATA%/Claude-3p

受管副本：
<test-root>/app
<test-root>/bootstrap
<test-root>/local/Claude-3p
```

这些是观察结果，不保证每个 Claude 发行版都使用同一目录。安装目录以当前可执行文件和资源布局为准，运行目录以实际进程参数为准。

## 完成的主界面测试

已完成手工原型与正式 CLI 两层验证。

手工原型：导入简体资源，补充语言白名单、资源 URL 和语言名称；显示中文侧栏、欢迎语、设置页、Code 首页、Gateway 提示，重启后仍为中文。

正式 CLI：导入官方简繁缓存 → `plan` → `prepare-copy` → 简体启动 → 退出 → `switch zh-Hant` → 繁体启动 → 退出 → `restore`。真实繁体界面显示“新增、自訂、推論設定、伺服器、連接器”。运行中恢复被拒绝，关闭后恢复的所有受管原文件哈希与备份一致，新增语言文件被移除，重复恢复安全返回。

新版基础键集为 35,441。仅看键存在时，最佳简体包命中 35,356 条；加入保守的占位符检查后，实际采用简体 35,345 条，85 条缺失与 11 条占位符不匹配消息回退英文。繁体采用 35,310 条，117 条缺失与 14 条占位符消息回退英文。动态资源两种语言均为 49/49。

匹配率不等于所有页面都视觉验收，也不保证每条资源都包含汉字。品牌名、模型名、官方资源本身的英文文案可能保留。

## 当前边界和下一步

- Windows 完整安装路径已实测；其他版本依赖结构锚点检查，不能声称全部支持。
- 首版在副本启动时固定选择 CLI 指定语言，应用内选择其他语言不作为永久偏好。
- 网关 profile 单独保存；不自动同步 magpie 后续密钥或端口变化。
- magpie 需要分别评估页面、Bun host、tool hook 和外部 companion。页面沙箱限制不等于所有插件只能做设置页，见 [扩展调研](magpie.md)。
- macOS 只实现检测和计划。修改 bundle 内资源会破坏签名，尚未实测安装、Keychain、Code、Cowork。
- 模型生成、工具执行、长会话和 Cowork VM 均未验证。自动化测试数量与范围以 [验证记录](validation.md) 为准。

本机的商店版安装文件未修改。临时开发者开关已恢复，正常模式语言恢复简体，正式 CLI 测试副本已完成恢复。早期供用户查看的中文演示副本可能仍保留，不能将其当作正式 CLI 的受管安装。

## 本轮补充：magpie 执行能力

README 已压缩为项目简介、快速入口和能力边界，完整步骤移至 `docs/windows.md`。GitHub `magpie-plugin` 标签下的插件进一步表明，独立本地管理工作台和宿主工具都是现实方案，页面沙箱不是整个扩展系统的能力上限。

新增 `integrations/magpie/server.mjs` 与 `controller.mjs`，通过正式 OpenCode tool hook 提供检测、计划、资源导入、副本创建、切换与恢复；所有路径来自用户保存的插件配置，写操作默认关闭。可选自动同步只在宿主存活时检查真实 3p Gateway，并只更新已安装且关闭的受管副本，不自动首次安装或替换系统快捷方式。

本机 `magpie 0.1.1234` 的隔离配置安装成功，但打包宿主缺少新版 tool RPC。官方源码宿主配合 Bun 1.4.2 的真实 RPC 实验成功枚举工具，调用 CLI 检测并返回受管副本 restored 状态，默认写入请求被拒绝。这比只模拟页面 bridge 更进一步，但不能表述为日常旧版宿主已支持自动汉化。

自动化测试增加到 22 项。完整管理按钮工作台尚未实现，自动写入在日常 magpie 下未实测。隔离测试使用单独的 XDG 配置和缓存，并关闭账号发现，未更改日常 magpie 的插件列表或账户。
